name: cagoule
description: Discover, deploy, modify and run open-weight models on Cagoule as Modelpack apps. Use when the user wants a model, LoRA, generated media, or a variant of an existing deployment.
---

Use the installed `cagoule` CLI through local command execution. Use `--json` for structured results and `cagoule COMMAND --help` for current arguments. The plugin contains guidance, not an executable.

On first use in a task, locate `cagoule` on PATH. If missing and Homebrew is available on macOS/Linux, install with `brew install anorak-games/cagoule/cagoule`. Installation and relevant CLI upgrades are authorized as part of using this skill; follow the host's execution permissions without asking for separate skill-level confirmation. Do not install Homebrew itself automatically. For Windows or a manual installation, download the matching OS/architecture archive from https://github.com/anorak-games/homebrew-cagoule/releases/latest, verify it against the release's SHA256SUMS, and place the executable on PATH. Native Windows supports the CLI but not `cagoule shell`; use WSL for shell workflows.

Run `cagoule --json version --check`. A newer version alone does not require upgrading. Upgrade when a requested command is missing, a relevant fix is available, or a compatibility failure calls for it. For Homebrew use `brew update && brew upgrade cagoule`; for manual installations use the verified release archive. Do not replace development builds automatically. If the version check is unavailable, say so and continue if the task can proceed. Recheck the version after upgrading. Old versions that lack `--check` can be identified with `cagoule --version`; upgrade when needed. Do not repeatedly retry a failed installation or upgrade without addressing its reported cause.

Run `cagoule --json status`. If authentication is required, run `cagoule login` once and allow the user to complete browser sign-in while the command waits. Do not request tokens or credentials. Access-denied errors need administrator attention; do not repeatedly reopen sign-in.

An app is a directory containing `modelpack.yml`. That one file declares everything: name, short description, inline Markdown long_description and usage, tags, base_model family, source_url for the implementation repository, an optional experimental flag, the platform stack family, the build command, the command that serves requests, machine types and memory, the Hugging Face volumes it reads, and JSON Schemas for inputs and outputs. The platform derives every deployment setting from it; there is no separate recipe, and the platform does not keep or export app source. Provide concise listing text, factual model capabilities, and practical usage guidance in the manifest. Use a stable family such as h3 or ltx for base_model; source_url links to the app's own source directory, not the upstream project it is derived from; that upstream is recorded in the app's `README.md`. Set `experimental: true` while the app is not ready to depend on: it may not be in a good working state and its inputs and outputs may change frequently. The web UI hides experimental apps from the model library behind a toggle, so use it for a new or in-flux app whose schema is still moving, and clear it in a later revision once the app settles. Weight repositories and pinned revisions belong in volumes.

App directories belong in the catalog, `https://github.com/anorak-games/cagoule-catalog`: one self-contained directory per app at the repository root, named exactly as the app, with source_url pointing at that directory on the default branch. The platform does not keep or export app source, so the catalog is where a deployed model is read, fixed and republished from later; the outcome to avoid is a running model whose source exists only on one laptop. This is a preference about where the source ends up, not a precondition for deploying. Work in a catalog clone, package and publish from the working tree as often as the model needs, and once it behaves, open a pull request to the catalog so the directory lands on the default branch. Nothing in packaging or publishing checks git state, and catalog changes go through review anyway, so do not ask the user to commit or push before a deploy. Follow the neighbouring directories rather than inventing a layout: a `README.md` stating what the model does and how it actually behaves, with a Provenance section naming the upstream implementation repository and commit, the weight repositories and revisions, and any upstream files modified (`modelpack.yml` stays the authoritative pin), vendored upstream code under `upstream/`, model code in a runtime package beside `app.py`, and a `tests/` suite the build command runs so a broken app fails packaging instead of publication. Keeping the source elsewhere is fine when it genuinely lives elsewhere, such as an app already in a repository the user maintains; source_url should still resolve to it.

Every command that starts remote work already waits for it. `deploy` returns when the revision is ready, `run` when the request has succeeded, `logs --follow` when the request or build reaches a terminal state, and `shell ssh -- COMMAND` when the command exits, with its exit code. The waiting is inside the CLI: it polls every two seconds, labels the stage it is in, and backs off and reattaches through a dropped network, a sleeping laptop or a 5xx, without limit and without losing the remote work. So run one of those commands in the foreground and let it block for as long as it takes, however long that is.

Do not write a script around them. No `while` loop over `request ID` or `package status ID`, no background job writing a status file, no `sleep`-and-recheck, no watcher tailing an output path, no scheduled wake-up to see whether a deployment landed. Such a script is a worse copy of the wait that already shipped, and the shapes below are why it hangs instead of failing loudly: it watches `stage` for a terminal value that does not exist, or `pending` for a ready state that never occurs, or greps `succeeded` from a job that ends `ready`, or misplaces `--json` and compares an empty string forever while the real error sits unread on stderr. It burns turns, and against `cagoule shell` it burns a billing GPU. If a command is slow, that is the remote work being slow, and the right response is to keep waiting in the foreground.

When reading one of these states, four details decide whether the reading means anything. `--json` is a global flag and Go stops parsing flags at the first non-flag word, so it must precede the subcommand: `cagoule --json request ID` works, `cagoule request ID --json` is a usage error that prints nothing on stdout and exits 2. Errors of every kind, usage and API alike, go to stderr while stdout stays empty, so a reading piped straight into `jq` yields an empty string rather than a failure. `status` is the only field that becomes terminal, and its vocabulary differs by resource: a request ends `succeeded`, `failed` or `cancelled`, while a packaging job and a revision end `ready` or `failed`. `stage` is not a progress bar to watch: it records the last stage entered and freezes there, so a succeeded request reads `stage: uploading_outputs` and a failed one reads `stage: processing` forever; no terminal stage value exists. And an app's JSON has no top-level `status` at all: it carries `name`, `current` and `pending`, each revision's status nested inside. A publication succeeds by the revision moving out of `pending` and into `current`, not by `pending` turning ready, so `pending` is null again the moment it worked; match it by `revision` or `artifact_digest`, since either may carry the digest a deploy printed.

Two cases genuinely need no wait. A one-off status reading, which is a single `cagoule --json request ID`, `describe APP` or `shell list` with nothing after it. And work deliberately left running across turns, which is submitted with `--no-wait` or `--detach` and then rejoined later with the blocking command that reattaches to it: `cagoule logs --request ID --follow`, `cagoule logs --job ID --follow`, or a rerun of `deploy` or `run` with the same operation name. Reattaching never duplicates the work.

1. Run `cagoule capabilities` and `cagoule --json apps`. CLI list commands collect pages; when using `cagoule api` directly, follow next_cursor even when a filtered page is empty. `cagoule --json describe APP` returns the current revision including its generated definition and input/output schemas; `cagoule run` handles all models.
2. For a new model, `cagoule hf search` and `cagoule hf inspect` to choose files. Prefer weights the platform has already replicated: `hf inspect` returns a `replicated` list for the repository and `cagoule --json volumes` shows every replicated selection with the apps using it; pinning one of those revisions with the same or a subset of its files publishes in minutes and adds no storage, so only pin a new revision when the model needs it. Then use `cagoule new` with a new directory at the root of a catalog clone, an explicit stack family from `cagoule capabilities` (for example python312-pytorch290-cu130), a machine type and runtime memory. It scaffolds `modelpack.yml`, a self-contained `app.py`, `pyproject.toml` and `.inferignore`; read a sibling directory for the rest of the layout. For a variant of an existing app, follow that app's source_url from `cagoule --json describe APP` to its directory, copy it to a sibling named for the variant, change `name` in `modelpack.yml`, and edit from there so the base and the variant stay side by side and diffable.
3. Edit `modelpack.yml`. Under `volumes`, declare each Hugging Face repository with its full commit SHA and the exact `files` the model opens, as paths or `**` patterns; nothing else exists at `/volumes/<name>` on the worker, and a pattern matching no file fails publication. Put structural validation in the `inputs` and `outputs` schemas; `default` is a hint for user interfaces and is never applied, so model code owns fallbacks. Keep `machine_types` in preference order and set `runtime_memory_gib` to peak host memory beyond weights, package and stack. Declare Python dependencies in `pyproject.toml`; torch and CUDA come from the stack, and the built package must stay under 2 GiB.
4. Implement `app.py`. One self-contained file holds pydantic `Input` and `Output` models, `setup(context)` loading the model from `context["volumes"]` onto `context["device"]` and returning state, `run(state, input, output_dir)` returning the output object and writing files under `output_dir`, naming them in the output by relative path, `teardown(state)` releasing the model, and the `serve()` loop itself: read a JSON line from stdin, dispatch on `command`, write one reply to descriptor 3 and flush. There is no library to install, no base class and no helper module to vendor. The scaffold and every catalog app carry the same `serve()`, so copy it unchanged instead of writing another one. An exception inside a command becomes `{"ok": false, "error": ...}` with a traceback on stderr and the loop keeps serving, so one bad request does not cost the loaded model. Input arrives exactly as submitted after schema validation. Printing to stdout or stderr is fine; both are request logs. Base weights and LoRAs are ordinary separate volumes, such as `base` and `lora`; loading them is model-specific code.
5. Run `cagoule validate DIR`, then `cagoule --json deploy DIR` for the usual remote package-and-publish workflow. It packages, publishes and waits for the revision to become ready before it returns; rerunning the same `deploy` reattaches to that build rather than starting a second one. For independent packaging, run `cagoule --json package app DIR --operation NAME`; it returns a job ID immediately, and `cagoule logs --job ID --follow` then blocks until that build is ready, failed or cancelled. Publish its artifact URL with `package publish ARTIFACT_URL`, then follow `cagoule logs --app APP --revision REV --follow` until that revision is ready or failed. `package upload ARTIFACT_DIR` uploads an existing local artifact. Use `package cancel ID` to cancel remote packaging. Publication replicates the package and synchronizes declared volumes to all regions; `volumes` and `volume ID` show replication and errors. Failed publication preserves the previous ready revision. Preflight validates against the hourly hardware catalog, not live GPU capacity or successful inference; let temporarily unavailable catalogs populate rather than launching inference to bypass validation.
6. Run a small generation against the exact ready revision using `cagoule --json run APP --revision REV --input @input.json --operation NAME`, adding `--logs` to stream the model's output and `--download DIR` to save its files. That one command submits, waits, and returns the finished request, so it is the whole step. Reuse the operation name after an interrupted submission; choose a new one for an intentional repeat. `--no-wait` is only for a generation deliberately left running across turns, and then `cagoule logs --request ID --follow` waits for it later. Upload local input files with `cagoule upload`; its renewable URL is refreshed by the API on submission.
7. `cagoule --json request ID` reports one request's current state; use it for a single status reading, not in a loop. Read `logs --job ID` for packaging failures and `logs --request ID` for runtime failures. Fix, rebuild and republish as necessary; manifest changes require a new build. Do not automatically retry inference. `cancel ID` stops a generation; `logout` only clears device login. Client interruption does not cancel cloud work: recover using job IDs, app/revision, request history and the same operation name. Packaging operation names also retain their inputs; choose a new name after changing source.
8. Return the app name, reproducible revision, request ID, result links, local files from `cagoule download`, and source location. If the source is not on the catalog's default branch, mention once that a pull request to the catalog remains, rather than treating it as part of deployment. Never put binary contents in text context.

Omit `tmp_memory_gib` for the default 4 GiB memory-backed `/tmp`. Increase it for large temporary intermediates such as decoded frames; it must stay within `runtime_memory_gib`, alongside CPU tensors and other working memory. Capacity does not preallocate RAM.

Stack names identify fixed runtime families; revisions provide compatible maintenance within a family, and apps always run on the family's current revision. Select another stack explicitly to change core runtime versions. Use remote packaging; employees need no local Python, Go, Docker or Google CLI for any of the above. Keep existing Terraform-managed models unchanged. No Terraform execution, fleet administration, private repositories, training, multi-node execution, streaming generation or promotion workflow. Gated Hugging Face repositories work when the platform's Hugging Face account has accepted their terms; if `hf inspect` reports the platform account has not been granted access, tell the user to accept the terms on huggingface.co as the platform account and retry, since the agent cannot do that itself.

`cagoule shell` provisions an ephemeral spot GPU box through the authenticated Cagoule API, carrying the stack and weights a `modelpack.yml` declares. It uses normal Cagoule sign-in and needs `ssh`, `git` and `rsync` on macOS or Linux; no Google Cloud credentials or `gcloud` are needed. The CLI generates a local SSH key under `~/.local/cagoule/ssh/` and connects directly to the box. Use `cagoule shell up --detach` in the app directory, then `cagoule shell sync && cagoule shell ssh -- pytest src/tests`, and `cagoule shell down` when finished. Each of those returns on its own; `ssh -- COMMAND` returns the command's exit code, so a test run is one foreground call and needs nothing built around it. Pass `--detach` whenever the box is driven by commands rather than typed at: plain `cagoule shell up` holds a heartbeat and prints uptime until it is interrupted, which never returns and leaves a GPU billing behind whatever is waiting on it. Commands select the box by signed-in owner, modelpack and checkout directory. Reattaching never applies an edited `modelpack.yml`; when `up` warns that the box was created from a different one, relay it and take the box down and up again rather than assuming the new volumes or machine are in place. `cagoule shell forward PORT...` tunnels a port on the box to `http://127.0.0.1:PORT` for a browser on the user's machine, taking `PORT` or `LOCAL:REMOTE`. Unlike every other command here it is foreground and blocking by design and never returns on its own: it holds the tunnel open, reconnecting through drops, until the user interrupts it, exactly as plain `cagoule shell up` holds a heartbeat. So it is for the user to run, not a step to put in a sequence; do not wrap it in a wait, a poll or a background job, and do not run it and then try to read its output. It sends no heartbeats, so it does not keep a detached box alive. Mention it when the user is iterating on model code that needs a GPU and republishing is too slow a loop. The default lifetime is one hour; `--lifetime` overrides it. The CLI displays estimated Spot compute charges, excluding disk and network. A box bills while it runs, so start one only when the user asks and remind them to run `cagoule shell down`. A detached box has no idle watchdog to reap it, so it bills for the full lifetime unless it is taken down; take it down as soon as the work on it is finished rather than at the end of the task. Relay missing-tool or sign-in errors to the user.

`cagoule comfy` is the ComfyUI equivalent and is what to reach for when the user wants to drive ComfyUI by hand rather than to iterate on an app's code. It needs no `modelpack.yml` and no directory: `cagoule comfy up --env NAME` provisions a box from a stack with ComfyUI already installed, starts the server, and forwards port 8188. Which form to run depends on who is driving the box, exactly as with `shell up`. When an agent starts it, run `cagoule comfy up --env NAME --machine NAME --detach`: it provisions, starts ComfyUI, waits for the server to answer on its port and then returns, leaving the server running on the box; it is one foreground call and needs nothing built around it. Plain `up` without `--detach` is the user's command: like `shell forward` it holds a tunnel and a heartbeat and never returns on its own, so it is for the user to run — do not put it in a sequence, wrap it in a wait or try to read its output. ComfyUI runs on the box rather than under either command, so Ctrl-C leaves it serving and a second `up` reattaches in seconds, and a user who wants the browser after an agent started the box detached just runs plain `up` themselves. Only `cagoule comfy down --env NAME` stops the billing, and it deletes the box the same way every other box is deleted. A detached box has no idle watchdog: its idle timer is set to its whole lifetime, four hours by default, so it bills for all of that unless it is taken down. Run `comfy down` as soon as the work on the box is finished rather than at the end of the task, and start a box only when the user asks. `cagoule comfy restart --env NAME` cycles the server on a box that is already running, which is how a newly added node pack gets registered; it returns on its own and is safe to sequence. `cagoule comfy ssh --env NAME -- COMMAND` runs a command on the box and returns its exit code, and is how the agent checks what the box actually has. The server listens on the box's own loopback at port 8188, so `cagoule comfy ssh --env NAME -- curl -s localhost:8188/object_info` lists every registered node, which is the way to confirm a pack loaded after `comfy restart`; a pack whose nodes are missing there failed at import, and the cause is in the serve log that `restart` reports, not in another restart. Whether a weight landed is a listing of `models/KIND` under the base directory the box's serve log names, or the loader's options in that same `object_info` output. Always pass `--env` when running these for the user: omitted on a terminal, `comfy up`, `down` and `ssh` stop and offer an interactive list, which a scripted run cannot answer. `cagoule machines` lists the GPUs with the machine type carrying each and its Spot price, cheapest first; there is no region to choose, since the platform places the box where capacity looks likeliest and takes the cheaper zone between equals, and `cagoule comfy up --machine NAME` runs the box on one of them; on a terminal with no `--machine` the command asks interactively, so always pass `--machine` when running it for the user rather than leaving them a prompt, and prefer the default by passing nothing only when the box is being started by hand. A named machine is a narrower search for Spot capacity than the default, so relay a capacity error rather than retrying it. Hardware is fixed when the box is created; `--machine` takes effect only after `cagoule comfy down`.

`cagoule env` manages the weights such a box has. An environment maps a destination path on the box to a replicated file, and the record is a JSON file on the user's own machine at `~/.cagoule/environments/NAME.json` — `cagoule env list` prints the path and needs no network. Reading or editing that file directly is legitimate when the user asks for something the commands do not cover, but prefer the commands, which validate the destination and start replication. The platform stores nothing about an environment: it is sent the whole thing when a box is created or updated. `cagoule env new NAME`, `cagoule env add NAME KIND SOURCE`, `cagoule env show NAME`, `cagoule env rm NAME PATH`. These return on their own and are safe to sequence. `add` and `rm` also update a box that is already running, materializing what is new and removing what is not, which is how disk space is reclaimed on a live box; a weight is usable immediately, while a newly added node pack needs `cagoule comfy restart --env NAME` rather than taking the box down. When the box cannot be reached the environment change still stands and the command says how to pick it up. Prefer weights the platform has already replicated, exactly as when pinning volumes: `hf inspect` reports them, and adding one moves no bytes and is ready at once. Without `--revision` the repository's current revision is resolved and recorded, so the environment keeps meaning the same weights. `cagoule comfy up` creates the environment it names if it does not exist, and an environment still replicating holds the box rather than failing it. Environments and volumes share the same blobs, so removing an entry or deleting an environment frees nothing by itself, and deleting an environment deletes only the local record. KIND comes before SOURCE and is what decides the destination: `custom_node` takes a GitHub repository and lands at `custom_nodes/REPOSITORY`, and any folder ComfyUI reads — `vae`, `loras`, `checkpoints`, `diffusion_models`, `text_encoders` and the rest, listed by `cagoule env kinds` — takes a Hugging Face file and lands at `models/KIND/FILENAME`. Read the kind off the workflow or the repository layout rather than guessing; an unrecognised kind is refused, and the wrong one puts a weight where ComfyUI will not look, which shows up as an empty loader dropdown rather than an error. `--at` overrides the path for a file that must be renamed or nested. A node pack pins the default branch to a commit; pass `--revision COMMIT` to pin an exact one, and re-run the same command to update, which reports what moved and does nothing when there is no change. Packs are not replicated: the box fetches the pinned commit itself when it starts, so adding one is immediate, but a box start needs GitHub reachable and a force-pushed or deleted repository fails the box rather than silently changing it. Relay that failure rather than retrying it. Packs are replicated as they are and never installed, so a pack needing a Python package the stack does not provide will fail to register its nodes; check `cagoule capabilities` for what the stack has before suggesting one, and read the failure out of the serve log rather than retrying.
